# 16 · 部署与 CI 指南（Rocky Linux + nginx + Jenkins）

> 适用范围：集智 AI OPC 官网（Next.js 15 App Router）部署到 Rocky Linux 9，
> 前面用已有的 nginx 做 TLS 终止与反向代理，发布走 Jenkins 流水线。

---

## 1. 先说结论：为什么不能做成纯静态站丢给 nginx

很多 Next.js 项目的默认答案都是「导出静态 HTML，nginx 直接托管」。**本站不行**，
原因不是技术偏好，而是代码里存在四类必须在 Node 进程里跑的路由：

| 路由 | 代码位置 | 为什么静态化会坏 |
|---|---|---|
| `/api/leads`（POST 留资） | `src/app/api/leads/route.ts` | 静态导出没有 POST handler，表单提交 404 |
| `/api/admin/*`（线索/新闻 CRUD） | `src/app/api/admin/**` | `force-dynamic` + 服务端会话校验，导出后全部失效 |
| `/api/og`（动态分享图） | `src/app/api/og/route.tsx` | `runtime = 'nodejs'`，**运行时**生成 1200×630 PNG |
| `/api/search`（站内检索） | `src/app/api/search/route.ts` | `force-dynamic` |
| `/admin/*`（管理后台） | `src/app/admin/**` | `force-dynamic`，且要读 httpOnly 会话 cookie |
| 多个内容页 | `revalidate = 300/600/3600` | ISR 依赖**服务端**再生成，静态导出后内容永远不更新 |

所以架构是固定的：

```
浏览器
   │  HTTPS
   ▼
nginx (:80/:443)          ← TLS 终止、反代、静态资源长缓存
   │  HTTP  127.0.0.1:3000
   ▼
Node (standalone server.js) ← Next.js 应用：页面渲染 + API + ISR
   │  Supabase / 火山方舟 / Resend
   ▼
```

**nginx 的角色是反向代理，不是静态文件服务器。**

> 如果将来真要「纯静态 + CDN」，前提是把后台、留资表单、OG 图、检索全部拆成独立服务
> （静态站 + 独立 API + 独立 OG 服务）。那是一次架构改造，不是配置改动。

## 2. 部署资产清单

| 文件 | 装到哪 | 作用 |
|---|---|---|
| `infra/bootstrap-rocky.sh` | Rocky 上执行一次 | 装 Node、建用户/目录、装 systemd、SELinux/firewalld 放行 |
| `infra/nginx/jizhi.conf` | `/etc/nginx/conf.d/jizhi.conf` | 反向代理站点配置 |
| `infra/systemd/jizhi.service` | `/etc/systemd/system/jizhi.service` | 进程守护（systemd 版） |
| `scripts/build-release.sh` | 构建机 / Jenkins | 构建 standalone + 打包 + 校验 |
| `scripts/deploy-release.sh` | Rocky 上执行 | 原子发布 + 健康检查 + 自动回滚 |
| `Jenkinsfile` | Jenkins job 根目录 | 声明式流水线 |

`pm2.config.cjs`（仓库原有）继续可用，`deploy-release.sh` 支持
`PROCESS_MANAGER=pm2` 切换。默认推荐 systemd，理由见 §7.2。

## 3. 环境变量：三类，分清就不会踩坑

这是本项目最容易出错的地方。填错地方的后果是「不报错，但功能不对」。

### 3.1 构建期内联（`NEXT_PUBLIC_*`）

由 Next.js 在 `pnpm build` 时**写死进产物**（客户端 chunk + 预渲染 HTML + 预渲染的
`sitemap.xml`）。**只在服务器上设运行时变量不生效** —— 实测过：探针值只出现在构建产物里。

| 变量 | 作用 | 放哪 |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | canonical / sitemap / robots / og:url | Jenkins 构建参数 |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase 项目地址 | Jenkins 凭据 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon key（前端可见） | Jenkins 凭据 |

**改域名 = 改这里 + 重新构建**，不是重启服务。

### 3.2 运行时读取（服务端密钥）

进程启动时读，改完重启即生效。

| 变量 | 作用 |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | 数据库最高权限，**绝不可加 `NEXT_PUBLIC_` 前缀** |
| `OPS_TOKEN` | 后台恢复主口令通道（留空 = 关闭该通道） |
| `LEAD_NOTIFY_WEBHOOK` | 新线索 IM 通知 |
| `LEAD_NOTIFY_EMAIL_TO` / `_FROM` / `RESEND_API_KEY` | 新线索邮件通知 |
| `S3_ENDPOINT` / `S3_REGION` / `S3_BUCKET_NAME` | 后台媒体上传（Supabase Storage S3 兼容端点，桶 `weboss` 公开读） |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | Supabase Storage 的 S3 密钥（控制台 Storage → S3 Access Keys 生成） |

放在服务器 `/etc/jizhi.env`（`600`，属主 `root:jizhi`）。

> 后台会话签名密钥是从 `SUPABASE_SERVICE_ROLE_KEY` + `OPS_TOKEN` + `NEXT_PUBLIC_SUPABASE_URL`
> 派生后 SHA-256 的（`src/lib/admin/accounts.ts`）。所以
> **构建期注入的 `NEXT_PUBLIC_SUPABASE_URL` 要和线上实际用的库一致**，
> 否则后台登录后立刻掉线。

**媒体上传链路（2026-10 整改后统一形态）**：封面 / 各模块图片字段 / 富文本正文配图 /
媒体库「⬆ 上传图片」都走同一条路——前端 POST `/api/admin/uploads` 拿预签名 PUT URL
（`src/lib/admin/storage.ts` 手写 SigV4，零 AWS SDK 依赖）→ 浏览器直传 S3 端点 →
落库公开 URL（`<SUPABASE_URL>/storage/v1/object/public/weboss/<key>`）。
⚠️ 该网关按**收到的全部查询参数**重算签名，预签名 URL 必须带
`X-Amz-Content-Sha256=UNSIGNED-PAYLOAD` 查询参数——漏掉即 403 SignatureDoesNotMatch
（`test/admin-storage.test.ts` 有回归锚点）。S3_* 未配置时各表单降级为仅可粘贴外链 URL
（接口返回 503，前端提示），不影响既有功能。仅放行 jpg/png/webp/gif/avif，单图 ≤10MB。

### 3.3 构建期自检

`scripts/build-release.sh` 开头会检查三个构建期变量是否都非空，缺一个直接退出非零 ——
避免把「错的域名」或「错的数据源」发到线上。

## 4. 手工发布（首次上线 / 应急 / 不想上 CI 时）

### 4.1 一次性初始化（Rocky 上，root）

```bash
# 在服务器上（需要仓库源码，或把 infra/ 目录传上去）
bash infra/bootstrap-rocky.sh
```

它会：装 Node 22 LTS → 建 `jizhi` 系统用户与 `/opt/jizhi/{releases,current}` →
生成 `/etc/jizhi.env` 骨架并设为 `600 root:jizhi` → 装 systemd 单元 →
放行 SELinux `httpd_can_network_connect` → firewalld 放行 80/443。

### 4.2 填运行时密钥

```bash
vi /etc/jizhi.env          # 填 SUPABASE_SERVICE_ROLE_KEY / OPS_TOKEN / 通知配置
chown root:jizhi /etc/jizhi.env && chmod 600 /etc/jizhi.env
```

### 4.3 装 nginx 配置

先按实际情况改 `infra/nginx/jizhi.conf` 里的 **`server_name`** 和**证书路径**：

```bash
install -m 0644 infra/nginx/jizhi.conf /etc/nginx/conf.d/jizhi.conf
nginx -t && systemctl reload nginx
```

没有证书的话，用 certbot 签一张（`server` 的 80 端口段已放行 ACME 路径）：

```bash
dnf install -y certbot python3-certbot-nginx
certbot --nginx -d t.3cool.cc
```

### 4.4 构建并发布

```bash
# 构建机（需要 Node ≥22.15 + pnpm 12）
export NEXT_PUBLIC_SITE_URL=https://t.3cool.cc
export NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
export NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...
bash scripts/build-release.sh
# → release/jizhi-<sha>.tar.gz

# 传到服务器
scp release/jizhi-*.tar.gz release/jizhi-*.tar.gz.sha256 scripts/deploy-release.sh rocky:/tmp/jizhi-release/

# 服务器上执行
bash /tmp/jizhi-release/deploy-release.sh /tmp/jizhi-release/jizhi-<sha>.tar.gz <sha> /opt/jizhi
```

发布脚本会：校验 SHA256 → 解包到 `releases/<sha>/` → 校验入口/静态资源齐备 →
**原子切 symlink** → 重启服务 → 三点健康检查 → 不通过则**自动回滚**到上一版本 → 清理旧版本。

### 4.5 确认结果

```bash
ls -l /opt/jizhi/current          # → 指向 releases/<sha>
systemctl status jizhi
journalctl -u jizhi -f             # 实时日志
curl -I http://127.0.0.1:3000/     # 期望 200
```

## 5. Jenkins CI 配置

### 5.1 Jenkins 装在哪都行

流水线用 SSH 把发布包推到 Rocky，所以 **Jenkins 可以装在 Rocky 本机，也可以装在另一台机器**
甚至 CI 容器里。唯一要求是能 SSH 到目标机，且装有 Node ≥ 22.15 + pnpm 12。

> 装在 Rocky 本机上要留意：构建会吃 2~4GB 内存，和生产进程抢资源。
> 内存小的机器建议把 `next build` 放到构建机或容器里跑。

### 5.2 创建 Job

1. **New Item → Pipeline → name it**（如 `jizhi-opc`）
2. 勾选 **Pipeline script from SCM**
   - SCM: Git → Repository URL `https://github.com/cuizhenjie/jzopc.git`
   - Credentials: 私有库要选 GitHub 凭据；公开库留空
   - **Script Path: `Jenkinsfile`**
3. 保存后点 **Build with Parameters** 填参数并首跑

### 5.3 建凭据（Manage Jenkins → Credentials）

| ID | 类型 | 内容 |
|---|---|---|
| `jizhi-deploy-ssh` | SSH Username with private key | Rocky 的部署密钥，Username 填 `root` 或 `deploy` |
| `jizhi-supabase-url` | Secret text | `https://xxxx.supabase.co` |
| `jizhi-supabase-anon-key` | Secret text | anon key |

### 5.4 服务器上的 SSH 授权

推荐做法（Rocky 上）：

```bash
# 在构建机上生成密钥对（已有可跳过）
ssh-keygen -t ed25519 -C "jenkins@jizhi" -f ~/.ssh/jizhi_deploy

# 把公钥加到服务器
# Rocky root 账号：/root/.ssh/authorized_keys
# 或专用账号：/home/deploy/.ssh/authorized_keys
```

若用**专用 deploy 用户**而不是 root，给它免密 sudo（限定范围，别给 ALL）：

```
# /etc/sudoers.d/jizhi-deploy （用 visudo -f 编辑）
deploy ALL=(root) NOPASSWD: /bin/bash /tmp/jizhi-release/deploy-release.sh *
```

> Jenkinsfile 里发布命令是 `sudo -n bash .../deploy-release.sh`。
> 如果服务器上没有 `sudo` 包且你用 root 直连，把 Jenkinsfile 里那行的 `sudo -n ` 去掉。

### 5.5 流水线做了什么

```
Checkout → Toolchain → Install → Verify(typecheck/verify/test) → Build → Package → Deploy → Smoke
```

- **Build**：`withCredentials` 注入三个构建期变量后跑 `pnpm build:deploy`
- **Package**：`scripts/build-release.sh` 产出 tar + sha256，并 `archiveArtifacts` 存档
- **Deploy**：scp 发布包 → 服务器执行 `deploy-release.sh`（含健康检查与自动回滚）
- **Smoke**：从 Jenkins 机器走公网域名验 `/`、`/robots.txt`、`/api/leads`

**发布包存进了 Jenkins 构建记录** —— 手工回滚时直接下载 artifact 再传服务器即可。

### 5.6 日常发布

改代码 → `git push` → Jenkins 触发（webhook 或手动）→ 流水线跑完自动上线。

GitHub webhook 触发：仓库 Settings → Webhooks → Add webhook，
Payload URL 填 `http://<jenkins>/github-webhook/`，Content type 选 `application/json`，
事件选 `Just the push event`。Jenkins 侧装 `GitHub Branch Source` 插件才能收到 push 事件。

## 6. 回滚

### 自动回滚（默认开启）

`deploy-release.sh` 的健康检查不过 → 自动把 `current` 切回上一版本并重启 → 退出非零让
Jenkins 标记失败。站点不会停留在坏版本上。

### 手工回滚

```bash
# 1. 看有哪些版本
ls -lt /opt/jizhi/releases/

# 2. 直接切回某个旧版本
ln -sfn /opt/jizhi/releases/<旧sha> /opt/jizhi/current.tmp
mv -Tf /opt/jizhi/current.tmp /opt/jizhi/current
systemctl restart jizhi

# 3. 验证
curl -I http://127.0.0.1:3000/
```

或从 Jenkins 下载旧构建的 `release/jizhi-<sha>.tar.gz` 重新发布一遍。

## 7. 排障速查

### 7.1 Rocky 专属坑

| 症状 | 原因 | 处理 |
|---|---|---|
| nginx **502**，日志 `permission denied` | SELinux 拦截 nginx 连 3000 端口 | `setsebool -P httpd_can_network_connect 1` |
| 外网连不上 | firewalld 没放行 | `firewall-cmd --permanent --add-service={http,https} && firewall-cmd --reload` |
| 服务起不来，`Failed to set up mount namespacing` | `ReadWritePaths` 指向不存在的路径 | 已改为 `/opt/jizhi`（bootstrap 会预建） |
| systemd `ProtectSystem` 导致 ISR 不更新 | `.next/cache` 不可写 | `ReadWritePaths=/opt/jizhi` 已覆盖 |
| 应用能被公网直接访问（绕过 nginx） | `HOSTNAME` 没显式设成 `127.0.0.1` | Next 的 `process.env.HOSTNAME \|\| '0.0.0.0'`：Linux 上 `HOSTNAME` 默认是**主机名**，清空则退化成 `0.0.0.0` |

### 7.2 应用层症状 → 真实原因

| 症状 | 真实原因 |
|---|---|
| **整站白屏**，控制台无报错 | `.next/static` 没打进产物（`prepare:deploy` 会拦，漏了就是白屏） |
| 图标 / favicon 404 | `public/` 没拷进产物 |
| 分享图中文变方块 | OG 字体没进包（`prepare:deploy` 也会拦） |
| 改了内容线上不变 | ① `NEXT_PUBLIC_SITE_URL` 等构建期变量没重新构建；② nginx 对 HTML 加了 `proxy_cache`（**别加**，见下） |
| 后台登录后立刻掉线 | `NEXT_PUBLIC_SUPABASE_URL` 构建期值与线上实际库不一致 → 会话签名密钥对不上 |
| 页面偶尔变慢 / 内容更新滞后 | ISR 本地磁盘缓存 → **只能单实例**，不能多端口负载均衡 |
| 发布后 502 几秒 | systemd restart 有秒级空窗；`ExecStart` 指向 symlink，restart 会解析到新版本 |
| `nginx -t` 报 `$connection_upgrade` 未知变量 | `map` 必须写在 `http` 块内 —— `conf.d/*.conf` 正是在 http 块里 include，位置正确 |

### 7.3 nginx 三条硬约束（改配置前重读）

1. **不要对 HTML 加 `proxy_cache`** —— ISR 再生成会被缓存住，内容改了线上不变，且不报错。
2. **必须透传 `X-Forwarded-Proto` 和 `Host`** —— 否则 canonical / sitemap / og:url 会变成
   `http://127.0.0.1:3000`。
3. **只反代一个上游端口** —— ISR 缓存写本地磁盘，多实例内容不一致。

### 7.4 systemd vs pm2

| | systemd（推荐） | pm2 |
|---|---|---|
| symlink 切换后取新版本 | `restart` 必定重新解析 symlink | 需 `delete` + `start`（`reload` 会继续跑旧 cwd） |
| 开机自启 | `systemctl enable` | `pm2 startup` + `pm2 save` |
| 日志 | `journalctl -u jizhi -f` | `pm2 logs` |
| Rocky 原生度 | 是 | 需额外安装 |

两套配置都在仓库里，`PROCESS_MANAGER=systemd|pm2` 切换。
